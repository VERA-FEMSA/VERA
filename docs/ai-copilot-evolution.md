# Copiloto contextual de VERA

## Experiencia implementada

- El acceso flotante **Preguntar a VERA** abre un panel desde las pantallas protegidas. La página `/asistente` sigue disponible.
- En las tarjetas de riesgo y control, y en el expediente de auditoría, **Analizar con IA** abre el panel con ese registro en contexto. El servidor comprueba la visibilidad antes de incorporarlo; un ID ajeno recibe 404 sin revelar el título.
- Las sugerencias iniciales cambian según el rol. Una tarjeta de señales muestra conteos deterministas de riesgos altos, controles con efectividad inferior a 4, hallazgos abiertos, pendientes de prioridad alta y auditorías activas. Esos conteos no provienen del modelo.
- Las preguntas exactas «¿Cuántos riesgos altos hay/tengo?», «¿Cuántos controles por revisar hay?», «¿Cuántos hallazgos abiertos hay?», «¿Cuántos pendientes prioritarios hay?» y «¿Cuántas auditorías activas hay?» reutilizan esos indicadores **del alcance visible del usuario**. En el contexto de un riesgo autorizado, «¿Cuál es el nivel y el puntaje de este riesgo?» consulta sus campos. Estas respuestas llevan la marca **Dato calculado** y no llaman a Azure. Los filtros distintos del área exacta indicada abajo, las fechas, el riesgo residual y los análisis siguen la ruta generativa; no se presenta un indicador global como respuesta a un subconjunto.
- El filtro exacto por área es una excepción explícita: «¿Cuántos riesgos altos hay en el área Finanzas?» (también «en el área de Finanzas») cuenta **todos** los riesgos visibles del área cuyo nombre coincide, sin limitarse a los 20 registros enviados al modelo. Ignora diferencias de acentos, mayúsculas y espacios. El resultado enlaza a `/riesgos` con `level=Alto` y `area` exacta; la pantalla y la API aplican ambos filtros. Si el área no coincide con ninguna visible, se informa que no se encontró en lugar de afirmar que el conteo es cero. Otros filtros, como fechas, auditoría o responsable, no se calculan con esta regla.
- El usuario puede hacer preguntas de seguimiento. Las seis intervenciones recientes se envían como historial **no confiable** junto al contexto vigente. Cada expediente y el chat general conservan su propia conversación mientras siga abierta la aplicación, incluso al cambiar de módulo o cerrar el panel. Se mantienen hasta 12 hilos recientes y 40 mensajes por hilo en memoria; **Nueva conversación** elimina solo el hilo actual. Al recargar, cerrar sesión o abrir otra pestaña, se pierde el historial; no hay almacenamiento del chat en Supabase ni en el navegador.
- El proveedor devuelve texto y IDs de fuentes. El servidor acepta solamente IDs que ya estén en el catálogo de registros visibles y construye enlaces internos. La interfaz separa **Registros citados** de **Registros relacionados**. Cada cita muestra una copia de campos básicos consultados por el servidor: estado/avance de auditoría, nivel/puntaje de riesgo, efectividad de control, estado de hallazgo o prioridad de pendiente, según el tipo. También muestra la hora de consulta de la respuesta. La hora es la del acceso a los almacenes, **no** la última modificación de cada registro; el enlace puede abrir un valor más reciente. Un ID válido y sus campos no demuestran por sí solos que toda la explicación generada sea correcta.
- La selección de contexto prioriza el expediente enfocado, IDs y términos de la pregunta, y estados como riesgo alto, auditoría activa o control inefectivo. Se mantienen los conteos de todos los registros visibles; si el contexto contiene solo una muestra de un módulo consultado, la respuesta muestra un aviso. Una muestra no debe describirse como la lista completa.
- Azure se consulta en modo JSON y el servidor rechaza respuestas incompletas o de formato inválido. [La documentación de Microsoft](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/json-mode) aclara que JSON válido no garantiza un esquema ni exactitud factual; por eso el servidor valida la estructura y los IDs recibidos.
- El asistente puede proponer borradores de próximos pasos, pero no tiene herramientas de escritura ni permisos para aprobar o cambiar expedientes.
- En el contexto de una auditoría, **Preparar briefing** calcula estado, avance, riesgos vinculados, controles asociados, hallazgos y pendientes del usuario desde todos los registros que su rol puede leer. Cada registro visible enlaza al módulo correspondiente y muestra sus campos básicos. Se presentan hasta diez por sección y se indica el total calculado. Azure propone un solo siguiente paso como borrador; si no cita una fuente autorizada, si falla o si está desactivado, se omite la sugerencia y los hechos calculados permanecen visibles. Una cita válida confirma la pertenencia de la fuente al alcance, no la exactitud semántica de la frase generada.

## Alcance y permisos

El backend verifica la sesión y vuelve a consultar los almacenes en cada pregunta. Para `AUDITOR`, incluye auditorías asignadas, riesgos propios y controles/hallazgos relacionados. Para `SUPER_ADMIN`, `DIRECTOR`, `GERENTE` y `JEFATURA`, la lectura actual de esos módulos es de portafolio completo; el copiloto replica ese alcance existente. No se considera que la interfaz o el prompt sean controles de autorización. Si cambian los permisos de los módulos, debe cambiar también esta política de lectura.

El modelo recibe campos reducidos, hasta 20 registros por tipo, conteos de todo el conjunto visible y hasta tres evaluaciones recientes del expediente enfocado. No recibe archivos de evidencia, contraseñas ni claves. El catálogo de fuentes se construye en el servidor. El historial que envía el navegador se limita a seis entradas de hasta 800 caracteres cada una y nunca amplía el conjunto de registros autorizados.

## Contrato de API

| Ruta | Uso |
| --- | --- |
| `GET /api/assistant/status` | Disponibilidad de Azure y almacenes requeridos. |
| `GET /api/assistant/brief` | Señales deterministas según los registros visibles del usuario. |
| `POST /api/assistant/ask` | `{ question, history?, focus? }`; `focus` admite `audit`, `risk`, `control` o `finding` y un ID visible. Devuelve `answer`, `mode` (`computed` o `generated`), `citations` con campos `facts` permitidos por tipo, `references`, `coverage` (muestra consultada frente a total visible), `asOf` (hora ISO de consulta), `durationMs` y `usage` (nulo para cálculo). Para un conteo exacto agrega `metric` con clave, etiqueta, valor y enlace; el de área agrega `filter.area`. |
| `POST /api/assistant/dossier/:auditId` | Briefing de una auditoría visible. Devuelve fuente de la auditoría, cuatro secciones con `total`, `shown` e `items`, hora de consulta y una sugerencia opcional con citas. Máximo cinco solicitudes por usuario cada 15 minutos. Responde 404 para expedientes fuera de alcance sin revelar el título. |

La respuesta HTTP lleva `Cache-Control: no-store`. Se mantienen el límite por usuario y la desactivación por `VERA_AI_ENABLED=false`. Los indicadores también requieren la disponibilidad configurada del asistente y los almacenes persistentes en producción. El presupuesto mensual de Azure **avisa**, pero no bloquea el gasto. La telemetría distingue `VERA_AI_COMPUTED` de `VERA_AI_ANSWER` y registra duración, rol, estado y tokens cuando aplica; no registra preguntas, respuestas ni contenido del contexto.

## Evaluación reproducible

Para una comprobación puntual de la **versión publicada** sin copiar claves Azure, usa la [guía de aceptación en producción](ai-production-acceptance.md). Requiere una cuenta activa de VERA; separa lo observado sin sesión de lo que falta verificar con datos y roles reales.

Desde `backend`, `npm run ai:eval` ejecuta ocho consultas **sintéticas** al despliegue Azure configurado: dato con fuente, ausencia de información, instrucciones maliciosas en un registro y en el historial, historial que intenta ampliar permisos, lista parcial, flujo de gobierno y borrador sin ejecución. Cada línea JSON informa el caso, estado, verificaciones individuales, duración y tokens; el resumen informa casos aprobados, latencia p50/p95 de respuestas recibidas y suma de tokens. `npm run ai:eval -- --list` enumera los casos sin llamar a Azure; `npm run ai:eval -- --case=dato-y-fuente` ejecuta solo uno. La salida evita preguntas, respuestas, contexto y claves. El código sale con 0 si pasan todos los casos seleccionados, 1 si falla alguno y 2 si faltan variables o el argumento es inválido.

La ejecución con Azure requiere `VERA_AI_ENABLED=true`, `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY` y `AZURE_OPENAI_DEPLOYMENT` en el entorno local del operador. Hace llamadas de pago al modelo, no consulta Supabase y no escribe archivos. Las verificaciones textuales son **heurísticas de regresión**, no una certificación semántica: un aprobado no demuestra precisión general, ausencia de filtraciones ni permisos reales por rol. El total de tokens no calcula costo. Las pruebas unitarias del evaluador se ejecutan en CI sin Azure; los ocho casos reales son manuales para evitar costo y variabilidad. Revisar manualmente respuestas de todos los roles con datos autorizados antes de declarar aceptación de producción.

Los escenarios automatizados de API y navegador cubren contexto, permisos, memoria de conversación, citas con campos y hora de consulta, conteos exactos sin llamada a Azure, filtro de área exacto con enlace al registro, filtros que deben volver al modelo, indisponibilidad, navegación y diseño móvil. CI no llama a Azure; usa un proveedor simulado para evitar costo y resultados variables.

## Publicación y operación

1. Revisar el PR y sus controles de calidad antes de fusionar con `main`.
2. Sincronizar el fork `CarlosSanchezGutierrez/VERA` con el `main` del equipo, revisar el SHA desplegado en `salva-ventures/vera` y confirmar estado `READY`. Un merge en el repositorio del equipo no sincroniza automáticamente el fork.
3. Comprobar con cuentas reales por rol que el panel no muestre registros ajenos, que cada enlace abra un expediente visible y que el modelo admita ausencia de datos. Evitar capturas con información sensible.
4. Medir duración, 429/5xx, tokens y gasto. Si el proveedor presenta errores, cambiar `VERA_AI_ENABLED=false` en Production y redesplegar.

## Límites y siguiente evolución

El chat no persiste al recargar la página o cerrar sesión. Las fuentes citadas son IDs de registros, no fragmentos textuales verificados. El briefing muestra campos calculados y un borrador separado, pero no verifica automáticamente cada afirmación libre de Azure. La búsqueda por relevancia usa reglas léxicas y estados, no embeddings ni búsqueda semántica. No se indexa el contenido de evidencias en este incremento. El panel no envía notificaciones proactivas, simula escenarios ni ejecuta flujos. Esas capacidades requieren diseño de datos y permisos por documento, indicadores de calidad y aprobación humana antes de agregar acciones.
